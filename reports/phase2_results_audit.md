sweep. No new training experiments were run for this audit. All numbers below are generated by `scripts/audit_phase2.py` from the
**frozen** snapshot (tables at the end of this file and in `reports/tables/phase2_*.csv`).

## 2. Per-experiment verification (21/21)

Each experiment was checked for: record exists; status completed with no error; training history exists; checkpoint exists **and loads** (model
structure rebuilt, weights/buffers loaded); all six test metrics present and finite; configuration present; seed recorded and equal to the
config seed; git commit recorded; timestamp; latency and storage fields present. **21/21 pass every check; no field was silently zero.**

Stronger check: every checkpoint was re-evaluated on a test split rebuilt from the recorded config. Recomputed vs recorded metrics: max |Δaccuracy|

## 3–5. Statistics, degradation, QAT vs PTQ

See the generated tables below. Statistical caveat: **n = 3 seeds**. Standard deviations are sample SDs (ddof = 1) and are themselves very
uncertain with n = 3; no significance tests are reported and none should be inferred. "k/3 seeds" counts are descriptive. The seed controls the
100k subsample, the split, the initialization and the shuffling, so SDs include data-sampling variance.

Main readings (mean ± SD over seeds, paired against FP32 of the same seed):

- **FP32:** ROC-AUC 0.9340 ± 0.0014; accuracy 0.7531 ± 0.0045.
- **INT8 PTQ:** ΔAUC −0.00006 ± 0.00008 (−0.006%); Δaccuracy +0.00002 ± 0.00062. Indistinguishable from FP32.
- **INT6 PTQ:** ΔAUC −0.0015 ± 0.0004 (−0.16%); Δaccuracy −0.0024 ± 0.0015. Small, same sign in all seeds.
- **INT4 PTQ:** ΔAUC −0.064 ± 0.036 (−6.8%); Δaccuracy −0.124 ± 0.064. **Highly unstable**: per-seed AUC ranges 0.835–0.909.
- **INT8 QAT:** ΔAUC +0.0004 ± 0.0009; **INT6 QAT:** −0.0002 ± 0.0007; **INT4 QAT:** −0.0096 ± 0.0024 (−1.0%), Δaccuracy −0.016 ± 0.003.
- **QAT − PTQ (ΔAUC):** INT8 +0.0005 ± 0.0010 (QAT higher in 2/3 seeds; accuracy/F1 3/3 but ≤ 0.003); INT6 +0.0013 ± 0.0006 (3/3);
  INT4 +0.054 ± 0.035 (3/3).

Correction to an earlier statement: the earlier single-seed write-up ("INT4 PTQ collapses 9.9 points, QAT recovers most of it") described one draw
of a highly variable quantity. The three-seed picture is: INT4 PTQ loses 12.4 ± 6.4 accuracy points on average (range of per-seed AUC drops
−0.098 / −0.027 / −0.067 for seeds 42 / 123 / 2026; accuracy 0.572 / 0.705 / 0.612), INT4 QAT loses 1.6 ± 0.3.
**Device sensitivity of INT4 PTQ:** the same seed (42) on CPU (earlier phase) gave accuracy 0.6507 / AUC 0.8832; on CUDA, 0.5716 / 0.8353.
FP32 and INT8 agree across devices to ≤ 1e-3 accuracy; INT4 PTQ differs by 8 points. INT4 PTQ is chaotic with respect to tiny numerical
differences, so single-run INT4 PTQ numbers have little meaning.

**Fairness caveat for QAT vs PTQ (not resolved by existing data):** the QAT pipeline trains FP32 and then fine-tunes 7 additional epochs; PTQ
gets no additional training. QAT therefore receives more optimization than PTQ, and the small INT8/INT6 QAT advantages (and QAT ≥ FP32 at INT8)
are within ~1–2 SD and cannot be attributed to quantization-awareness. A compute-matched control (FP32 fine-tuned for the same extra epochs) does
not exist. The large INT4 gap is not explainable by extra training (extra FP32 epochs cannot repair a rounding cliff) but is untested.

## 6. Model size

The registry field `estimated_size_mb` is **not** a file size. It is `weights × bits/8 + biases × 4 bytes` (analytical, bit-packed equivalent).
It was therefore renamed `theoretical_weight_storage_mb` in the reporting layer (frozen records keep the original key). Audit of the actual artifacts:

- All checkpoints store float32 tensors (21–24 kB regardless of precision; QAT checkpoints also store a bool flag). **No bit-packed artifact exists.**
- Quantization is genuinely applied: stored PTQ weights have ≤ 2^bits distinct values per layer in all 9 PTQ checkpoints (INT4: 13–16; INT6: ≤ 59; INT8: ≤ 186).
  QAT checkpoints hold latent float weights (1024/2048/1024/160 distinct values, i.e. all unique); applying the fake-quantizer used at forward time
  yields ≤ 2^bits levels in all 9 QAT checkpoints (INT4: 14–16).
- Theoretical storage: FP32 17,556 B; INT8 4,788 B; INT6 3,724 B; INT4 2,660 B (ratios 3.7×/4.7×/6.6×, not 4×/5.3×/8×, because 133 bias values stay FP32).
- Not quantized by this implementation: inputs, the output logits, biases, accumulators. "INT8 everywhere" is therefore not what is simulated.

## 7. Latency methodology

Implementation (`hardware/latency.py`): batch size 1, 10 warm-up forward passes, 100 timed repetitions, `time.perf_counter`, `torch.cuda.synchronize()`
after warm-up and after every timed forward on CUDA; random input; model in eval mode; the registry keeps mean and p95 (std/p50 were not stored). All 21 runs
used the **same device (CUDA)**; earlier CPU-phase latencies must not be compared with them.

What the numbers mean: batch-1 GPU latency of a 4k-parameter MLP is dominated by Python/kernel-launch overhead. The fake-quantization wrappers call
`.item()` (host–device synchronization) for ranges inside the forward pass, and QAT recomputes weight min/max every call. The measured ordering
(FP32 0.46 ± 0.19 ms < PTQ 1.8–2.1 ms < QAT 4.4–4.7 ms) is **simulation overhead, not a property of quantized hardware**. The FP32 SD is 42% of its mean and
some runs shared the machine with other jobs, so latency is indicative only. These numbers must not be used for any deployment claim.

## 8. hls4ml C-simulation (audit)

Categories kept separate throughout: (1) PyTorch inference — measured; (2) hls4ml *conversion* — produces C++ with `ap_fixed` types, no number;
(3) hls4ml **C-simulation** — bit-accurate host-CPU execution of that C++ — *simulated*; (4) HLS synthesis (Vivado/Vitis) — **not performed**;
(5) physical FPGA — **not performed**.

Configuration used (read from the generated project, `defines.h`/`parameters.h`/`hls4ml_config.yml`): backend Vivado, `io_parallel`, `Strategy: Latency`,
ReuseFactor 1, ClockPeriod 5 ns (unused without synthesis). Input, weights, biases, **accumulator**, layer outputs and result are all the *same*
`ap_fixed<W,6>` (default precision applied uniformly); softmax is not part of the converted graph (logits compared by argmax). Rounding and overflow
are not specified in the typedefs, hence the C++ `ap_fixed` defaults apply: **truncation (AP_TRN) and wrap-around (AP_WRAP)** — inferred from the generated
code, not stated by a config option. The activation lookup-table type is `ap_fixed<18,8>` (ReLU does not use it). A single FP32 model (EXP_S42_JET_FP32) and 15,000 test jets were used.

|---|---:|---:|---:|
| <8,6> | 2 | 0.2021 | 0.1624 |
| <10,6> | 4 | 0.3541 | 0.3433 |
| <12,6> | 6 | 0.7255 | 0.8958 |

FP32 PyTorch accuracy on the same rows: 0.7495. Interpretation limits: (a) this is a *uniform, un-profiled* fixed-point format with a narrow accumulator and wrap-around
overflow — hls4ml workflows normally profile and set per-layer widths — so the 8–10-bit collapse says little about what an optimized FPGA design needs;
(b) it is a different quantization scheme from the project's calibrated per-tensor INT-N fake-quantization, so "INT8" results do **not** transfer to `ap_fixed<8,6>`;
(c) single model, single run; (d) no latency, II or resource data exists from C-simulation.

## 9. Hardware resources

LUT/DSP/BRAM/FF in all 21 records come from `SoftwareEstimateBackend` and carry `measurement_tier = "estimated"` (verified: the set of tiers across the
21 records is exactly `{estimated}`). The heuristic is `dsp = ⌈weights/reuse⌉`, `lut = ⌈1.5·dsp·bits⌉`, `ff = params·bits`, `bram = 0`; it is not calibrated
against any synthesis and, being linear in bit-width by construction, carries no information beyond that arithmetic. **No FPGA synthesis result exists.**

available simulated HEP dataset; it has **not** been validated on real detector data, and no conclusion here may be stated for detector-level

physics-motivated features) does not depend on detector effects, but detector-level or open experimental data would be needed to show that the findings survive detector resolution, pileup and calibration effects.

## 14. Answers

1. **Sensitivity to reduced precision:** negligible down to INT6 under this simulation; severe and unstable at INT4 without QAT.
2. **INT8:** preserves performance (ΔAUC −0.00006 ± 0.00008, PTQ).
3. **INT6:** small consistent loss (−0.16% AUC, PTQ); QAT removes it within noise.
4. **INT4:** PTQ −6.8% AUC on average with huge seed/device variance; QAT −1.0% and stable.
5. **QAT vs PTQ:** clear advantage only at INT4 (3/3 seeds, +0.054 ± 0.035 AUC); at INT8/INT6 differences are ≤ 0.0013 AUC, ~1–2 SD, and confounded by 7 extra training epochs.
6. **Precision vs cost:** theoretical weight storage falls 3.7×/4.7×/6.6× (INT8/6/4); measured software latency *rises* (simulation overhead); resource numbers are heuristics.
7. **What C-simulation tells us:** a bit-accurate fixed-point model of this MLP matches FP32 predictions ≥ 99.3% at 16 bits and still reaches 72.6% accuracy at 12 bits under a naive uniform format.
8. **What cannot be concluded without synthesis:** any LUT/DSP/BRAM/FF, latency, initiation interval, timing closure or power; and whether per-layer-optimized widths would work at 8 bits.
9. **Reproducibility across seeds:** FP32/INT8/INT6/QAT: tight (AUC SD ≤ 0.0024). INT4 PTQ: not reproducible (SD 0.037).
10. **Strongest defensible conclusion:** *In simulation, on this simulated dataset and this MLP, INT8/INT6 post-training quantization is practically lossless, INT4 post-training quantization with min/max calibration is unreliable, and quantization-aware fine-tuning makes INT4 stable at about −1% AUC.* Not established: that QAT beats PTQ at INT8/INT6, anything about hardware cost or latency, or generality beyond this dataset/architecture.

**Can we make a scientifically defensible conclusion? PARTIALLY** — the INT4-QAT-vs-PTQ and INT8/INT6-near-lossless statements are supported by 3 seeds; everything hardware-related and any generality claim is not.

# Addendum (Phase 3) — what later work changed in this audit's readings

This audit's text and tables are left as written (the frozen evidence is untouched). Later work refined four statements:

1. **§8 / §14-Q7 (C-simulation).** The 8–10-bit collapse in the default hls4ml mode is largely a truncation + wrap-around artifact: with rounding + saturation, `ap_fixed<12,6>` gives ΔROC-AUC −0.0005 and `<10,6>` −0.007 (`reports/numerical_consistency.md`). The audit's caveat (a) was correct and is now quantified.
2. **§3–5 (QAT vs PTQ).** The "fairness caveat" was tested with a compute-matched FP32 fine-tune control (5 seeds): extra epochs alone give +0.0004 AUC; QAT INT8 − control = +0.0001 ± 0.0007; QAT INT6 − control = −0.0005 ± 0.0006; QAT INT4 − control = −0.0101 ± 0.0023. QAT's INT8/INT6 advantage over PTQ is therefore not attributable to quantization-awareness. See `reports/REAL_HEP_RESULTS.md`.
3. **§3 (INT4 PTQ).** Two more seeds (7, 99) fell inside the n = 3 range (n = 5: ROC-AUC 0.8819 ± 0.0308, range 0.835–0.909). Checkpoint studies attribute part of the instability to calibration range and to the first layer (L0 weights, A0 activation).
4. **§7 (latency).** A controlled study (CPU and CUDA events, batch 1 and 4096) confirms the FP32 < PTQ < QAT ordering on both devices and at batch 4096, so it is emulation overhead; batch-1 timings remain noisy.
